# Native D3D runtime against the title's

crackdown, 2026-11-14: the in-game self-test (`--any360_d3d_selftest=true`, docs/D3D.md) runs each function the title's way and Any360's on the same random inputs, on a copy of the device, and compares every byte they write; the times are each side's median over 8 calls in a row. Generated by `tools/d3d_perf.py` at the end of each step.

65 cases, 0 calls different; Any360 1.07x to 183.33x the title's speed (median 1.56x).

In game:

- City at 60 FPS (input script): 2,312 draws a frame, 192 skipped, 0 failed, 33 resolves, as with the natives off; uncapped, the city at 307-373 FPS.
- Command buffer submission (D6): 14.1 command buffers a frame handed to the command processor directly (any360_direct_submit), none written into the ring; the frames identical with it off.
- Resource lock (sub_826AC8F0; the self-test cannot run it: the device comes from the title's global): in a dual run, 16,371 locks compared (13,033 writing PM4), 0 different; about 1,400 TSC ticks the title's, 370 Any360's (Any360's run second, caches warm).
- Shader flush in the city: 0.04% of its calls declined (a shader's own copy patched again), its vertex shader copies checked against the title's patcher (172,001) and link (19,001), 0 different.
- CPU range flush: the title's dcbf loops are no-ops in recompiled code, so Any360's does nothing (hence its ratio).
